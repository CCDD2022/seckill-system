# 2026-09-24 本地并发诊断

这是一轮单机开发诊断，不是可外推的正式容量承诺。数据生成于后续 HTTP Problem Details 和异步请求状态接口改造之前；当前代码尚未重新压测。原始程序输出见 [JSONL](2026-09-24-results.jsonl)，生成器的当前版本见 `cmd/bench_http/main.go`。

## 环境与口径

- macOS arm64，宿主机 8 CPU / 16 GiB；Docker Desktop 28.1.1，Docker VM 报告 8 CPU / 8.22 GB。所有服务和压测客户端位于同一个 Docker VM、同一私有网络。
- 单实例 HTTP 网关、秒杀服务、Redis 7、RabbitMQ 4、MySQL 8、预占 relay、订单创建消费者和库存对账服务。Redis 使用 AOF `appendfsync always`。
- 每轮创建新商品，初始库存等于请求数；每个请求使用独立且已写入 MySQL 的用户及有效 JWT，购买数量为 1。用户/商品创建、JWT 签发、容器启动均不计入请求计时。
- “受理吞吐”= HTTP 202 或 gRPC `success=true` 数量除以所有请求获得响应的耗时；“最终订单吞吐”= 最终落库订单数除以从发出第一批请求到轮询确认订单全部落库的耗时。轮询间隔 100 ms，因此后一指标有约 100 ms 量化误差。P99 统计接口响应时长，未包含后台排队至订单落库的单笔尾延迟。
- “默认 HTTP”两行保留网关限流：单 IP 秒杀 `300/s`、突发 `600`，全局 `1000/s`、突发 `2000`。其余 HTTP 行使用 `benchmarks/no-rate-limit.compose.yml` 把限流阈值调高，其他应用配置相同。gRPC 行直接调用内部秒杀服务，不经过网关/JWT/限流。

## 解读与限制

接口能在几十至几百毫秒的短突发内完成大量“预占受理”；订单真正写入 MySQL 的平均速度在本次样本中约 412–519 单/s。`5000 / 200` 的三轮最终订单吞吐为 438、412、519 单/s，中位数 438 单/s；响应 P99 为 29.0、36.9、32.4 ms，中位数 32.4 ms。把并发从 200 提到 500，没有明显提升受理阶段吞吐，却把一次测量的响应 P99 推至约 159 ms。订单创建消费者目前是单实例逐条落库，结合吞吐平台现象，**推测**后台落单是主要瓶颈；这还需要队列积压曲线和 CPU/SQL profiling 验证。

这是短突发诊断；关键 `5000 / 200` 场景重复三次，其余场景只有单次测量。各轮使用新用户和新商品，但顺序复用了同一个栈，MySQL 数据量随轮次增加；压测客户端也与服务争用 Docker VM 资源。没有持续 5–10 分钟的稳态负载、外部网络、峰值资源使用或失败注入同时压测。代码仍是本地 `codex/reliability-overhaul` 工作树，尚无固定提交，因此申请材料应在提交后重跑并附完整环境和原始结果。

## 复现入口

在专用项目启动完整栈并构建工具镜像后，运行例如：

```bash
docker compose -p seckill-bench up -d --build
docker compose -p seckill-bench build bench-http
docker compose -p seckill-bench run --rm --no-deps bench-http --requests 2000 --concurrency 200 --mode http
```

若要测无网关限流的 HTTP 路径，使用 `-f docker-compose.yml -f benchmarks/no-rate-limit.compose.yml` 重建该项目的 `api-gateway`，然后执行同一工具命令。只在专用测试项目中这样做；结束后可用 `docker compose -p seckill-bench down -v` 清理该测试项目的数据卷。
